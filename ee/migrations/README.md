# `ee/` migrations

SQL migrations for the tables of the `ee/` modules, applied by `neburyx migrate` only where the AI extension is loaded (an AI provider key is set and Ask, the summary or the assistant is on, or both `NEBURYX_PROFILE=enterprise` and `ai.preview: true` in the mapping file are set). They are recorded in a history table of their own, so a new migration of the Community product never sorts before one already applied here.

A file is named `NNNN-what-it-does.sql`, one statement list per file, in the order it must run. `0001-audit-events.sql` and `0002-ask-runs.sql` create the preview's audit table and the table of Ask runs, `0003-ask-plans.sql` created the table of Ask plans, tied the runs to it and indexed the audit table by trace ID, and `0004-drop-ask-plans.sql` drops that table and the plan column of the runs again (the stored plans went with the old Ask path; the runs stay), and `0005-ask-runs-intent.sql` adds the intent of a run, marking the rows written before it as `unknown`, and `0006-summary-runs.sql` creates the stored record of what the case summary sent to the model and what came back (no route reads it; it is removed after the retention period). `0007-assistant-runs.sql` creates the stored record of what each assistant turn sent to the model and what came back (no route reads it; it is removed after its retention period). `0008-assistant-threads.sql` creates the thread tables of the assistant (references and metadata only, no text of a question or an answer) and the trigger that clears a thread when its investigation is closed, archived or deleted. `0009-assistant-pending-confirmations.sql` creates the table of the confirmations of a heavy step that wait for the analyst (ids, who and where, status and expiry; never a value, an element or a result), lets a thread keep a turn that waited, and removes the waiting rows of an investigation with the thread rows when it is closed, archived or deleted. `0010-assistant-run-errors.sql` adds the class, the code and the type of the error a failed model call threw to the stored call record (short codes, never a message). `0011-summary-run-removals.sql` keeps the sentences the checks removed from a summary reply, with the reason (no route reads it). `0012-assistant-run-tools.sql` adds the names of the tools the model was bound to for each stored call (names only). `0013-assistant-thread-text.sql` adds to a stored turn of the assistant's thread the question as typed, the answer in its stored form, whether the mask was asked for and the version of the sensitivity it was classified under (nullable; cleared with the thread by the trigger of `0008`; rolled back by dropping the four columns). `0014-assistant-thread-person-epochs.sql` creates the count of how many times a person has cleared their own thread of an investigation (kept when the investigation is closed, archived or deleted; removed with the investigation row) and gives each stored run record the count its turn read (rolled back by dropping the column and the table). `0015-assistant-thread-list-index.sql` adds the index that the list of a person's chats reads (the person, the last turn, the thread id; rolled back by dropping it). A migration is forward-only: after `0015` the previous image cannot run against the database, and going back means restoring a backup.

## Rights

The first `neburyx migrate` gives the application role read and write rights on tables that the migration role creates later (see the "Rights on new tables" section of `services/api/migrations/README.md`). `audit_events` is append-only, so its migration takes `UPDATE`, `DELETE` and `TRUNCATE` away from every role but the owner, which leaves the application role with `INSERT` and `SELECT`. If you removed those default rights before the first migrate, the application role has no right on `audit_events` and the migration grants none: grant `INSERT` and `SELECT` on `audit_events` to the application role by hand.
