# UX tests

Browser tests of the web app: Playwright with Chromium, at 1440 × 900 (every spec) and 1280 × 720 (the specs listed under *Widths*), on a **built** copy of `apps/web` served by a small support server (`src/support-server.ts`) that answers the few API reads the pages make with synthetic bodies. No database, no Neo4j, no Docker.

From a fresh checkout:

```bash
corepack enable
pnpm install --frozen-lockfile
pnpm build
pnpm --filter @neburyx/web build:ux
pnpm --filter @neburyx/renderer-spike build:node
pnpm --filter @neburyx/ux-tests exec playwright install chromium
pnpm test:ux
```

`pnpm build` makes the production build in `apps/web/dist`; `build:ux` makes a second build (`apps/web/dist-ux`, mode `ux`) that carries the development pages and the canvas read-out the tests read. With an installed Chrome, set `NEBURYX_UX_CHROME` to its executable instead of installing Chromium.

The specs that switch source, follow deep links or use Home run against a third copy of the support server on port 4175, which lists a second source (`claims-demo`, the same profile under another ID) and a third that it lists but refuses the person (`restricted-demo`) beside the first; the other two servers list one. Every source it lists is connected and never tested until a spec changes it: `POST /__support/sources` takes a map of source ID to the fields of `GET /v1/sources` to change (`state`, `stateReason`, `lastTest`, `lastTestAt`, `mappingSummary`, `synthetic`, `demoCase`; each call replaces every earlier change, including a last test stored by a test run, and an unknown source, an invalid field or a change that leaves the source summary invalid, such as a demo case on a source that is not synthetic, is refused with 400 and changes nothing), `POST /v1/sources/{id}/test` answers a passing report and stores it as the source's last test, `POST /__support/forget-investigations` removes every investigation opened so far, so a spec can start from an install that has none, `POST /__support/hold-after-test` makes the `GET /v1/sources` that follows a test wait until `POST /__support/release`, `POST /__support/named-views` takes `{ count, lastEditedAt }` for the named views the investigation list counts (none until a spec sets them; a count of 0 goes with a `null` time and any other count with an ISO time, otherwise it is refused with 400), and `POST /__support/reset` puts everything back, the named views too (a spec that changes sources or named views resets before and after). Like the application's own server it serves the page for every address that is not a file, and treats only `/v1`, what is under `/v1/` and the two probe paths as the API.

`fixtures/profile.json` is the synthetic source profile the pages read: the banking pack's, as the API's profile builder makes it. `pnpm --filter @neburyx/ux-tests check:profile` (after `pnpm build`) fails when it is out of date; `node tools/ux/scripts/make-profile.mjs` rewrites it.

## Widths

Each spec runs at 1440 × 900 (project `laptop-1440`). The specs whose result depends on the width of the window also run at 1280 × 720 (project `laptop-1280`): the list `WIDTH_DEPENDENT` in `src/widths.ts`, which holds `ai-header`, `compare`, `evidence`, `first-run`, `help-menu`, `home-controls`, `inspector`, `layouts`, `page-shell`, `pattern-builder`, `pattern-run`, `pattern-run-long`, `patterns-keyboard`, `patterns-panel`, `saved-patterns`, `starting-hint`, `workspace-shell` and `zoomed-out` (a region that must stay inside the window, boxes that must not overlap, or figures kept per width). `ONLY_1280` holds `left-panel` and `short-canvas`, which are made for the narrow window and skip at any other width, so they run at 1280 only. The `benchmark` project runs the two benchmark specs alone and last, at 1280 × 720.

A spec joins a list when it reads the window size, checks a region against the window or the position of one box against another (the hint against the canvas centre, every node inside the canvas). A unit test (`src/widths.test.ts`) scans every spec for those markers and fails when a spec that has one is in neither list nor in `EXEMPT`, where it needs a written reason (for example it sets its own sizes). A spec with no marker runs at one width and asserts there what it always asserted.

## Shards

CI runs the specs as three shards (`--shard=<n>/3` over `laptop-1440` and `laptop-1280`) on separate jobs, and the benchmark project alone in a fourth (`--project=benchmark --no-deps`). The ports 4173 to 4175 are fixed and the support servers keep their state in memory, so shards must run on separate machines, never two on one.

## The check of the browser's default look

`tests/default-look.spec.ts` visits every product page and the states of it that hold controls (the list is `tests/support/product-pages.json`, and `tests/support/product-pages.ts` says how to reach each state), at both sizes, and fails when a visible button, selector or text field still has the browser's own look: its fill, border and radius are all equal to those of a fresh control of the same kind in an empty frame. A plain control gets the shared look from `apps/web/src/styles/controls.css` with nothing to do on the page's side; a control that has a class of its own and no look in that class is what the check finds, and its message says that a class used for layout only belongs on a wrapper. `class=""` counts as no class. The development pages (`dev/`) and checkboxes are not in the check.

Its limit: it cannot see a state or panel that a page gains unless the list names it. A feature that adds a state with controls to an existing page adds it to the list in the same change (an entry in `product-pages.json` and its way to reach it in `product-pages.ts`). A unit test in `apps/web` (`src/product-pages.test.ts`) fails when a product route has no entry.

`pnpm --filter @neburyx/ux-tests mutate default-look` removes the shared look of selectors and text fields from the built CSS and checks that the browser check fails on it.

## Checking that a test can fail

`pnpm --filter @neburyx/ux-tests mutate [keyboard|crossing|benchmark|evidence]` breaks the built app on purpose and runs the browser test that has to notice, three times: as it is, with the app broken, and with the source put back; it fails unless the first and last runs pass and the middle one fails on the test's own assertion. `keyboard` breaks the Legend key binding, `crossing` puts a 400 ms stall in the switch of the zoomed-out view (held to the runner limit, `NEBURYX_UX_PROFILE=runner`), `benchmark` puts a 25 ms stall at every pan and zoom (held to the runner threshold), and `evidence` leaves the source records out of the stored relationship's evidence panel (the scripted case `evidence-panel` of `tests/trust-a-relationship.spec.ts` has to notice). Each rebuilds `dist-ux` and puts the source back, also when it is interrupted. `NEBURYX_UX_CONFIG` names another Playwright configuration for these runs (for example one on other ports while another run holds 4173 to 4175).

## The scripted cases of "can I trust this relationship?"

`tests/support/trust-cases.ts` lists the cases (`TRUST_CASES`): an entity opens an inspector; each kind of relationship (stored with evidence, stored without, rule-derived, and aggregate) answers "why is this relationship here?" in the evidence panel, reached by the menu with the pointer, the menu with the keyboard or a row of the inspector; the panel takes the focus and gives it back on Esc; no element ID of the source and no address of a source record is on the screen; the screen says "relationship" and never "edge". A case is written in what a person sees and does, and runs in an *environment* (`TrustEnvironment`) that says how to reach each kind: this folder runs them in the development sample and over a stubbed API (`trust-a-relationship.spec.ts`, at both sizes). A later end-to-end test imports the list and brings an environment of its own over a real demo graph.

## The scripted pattern runs

`src/support-patterns.ts` answers `GET /v1/templates` (the presets of the profile, or none after `POST /__support/patterns-mode` with `{ "noPresets": true }`) and `POST /v1/templates/{id}/run`. The answer to a run is chosen by the `limit` the form sends, so a spec reaches each state with the form alone: 1 gives no match, 3 a run that waits until the client leaves it, 4 a busy source, any other limit the six-account ring; a `minShared` of 2 gives a heavy stop whose `continueLimit` follows the API's rule (25, lowered by the page asked for), and the same request with the continue flag gives the ring. The second source (`claims-demo`) declares the presets of the insurance pack (`fixtures/presets-insurance.json`, kept current by `make-profile.mjs` and checked by `check:profile`). Every answer is parsed by the contract before it is sent.

`POST /v1/patterns/validate` answers the contract's own check of the definition's shape and caps, and one scripted problem: a pattern that starts at a `merchant` is not valid (`unknown-entity-type` on `anchorType`). Every source lists `maxHops` 4. The pack definitions that the builder spec builds, with the conditions and the window it adds, are validated against the real mappings in `tools/demo-graph/src/pattern-packs.test.ts`. The builder spec also walks the editor's tab stops in the order of the design's keyboard frame, builds a two-step pattern with a condition and a window by keyboard alone, and breaks a later step with a change to the start and takes the change back.

The saved-pattern routes (`GET`, `POST /v1/patterns`, `PUT` and `DELETE /v1/patterns/{id}`, `POST /v1/patterns/{id}/copy` and `/run`) are answered in memory by `src/support-saved-patterns.ts`: three patterns of `banking-demo` at the start and after `POST /__support/reset` (one of the person's own that holds its starting entity, one shared by another person, one of the person's own that the mapping can no longer run, which answers `unavailable`), a stale version is `CONFLICT`, another person's shared pattern is `ACCESS_DENIED` for a change or a delete, a name the person already has on the source (a save, a rename or a change) is a `CONFLICT` with the reason `pattern-name-taken` (the copy route numbers its copies), and a run is the pattern run of the stand-in over the stored definition.

`src/support-pattern-runs.ts` answers `POST /v1/patterns/preview` (the definition in words the support server writes, with the bounds of the sources, parsed by the contract) and `POST /v1/patterns/run`. The run is scripted by the starting entity: `EMPTY-1` finds nothing, `HEAVY-1` stops as heavy (the same request with `continue` gives the page), `SLOW-1` waits until the client leaves it, `BUSY-1` answers a busy source, `PAGED-1` gives two pages (the first has a `nextCursor` and an exact count, the page read with that `cursor` has a lower-bound count), `LONG-1` gives two matches whose labels are as long as a mapping can make them (a long non-ASCII title, no title and a very long ID, many properties and an empty one); any other entity gets the ring (two matches of the pattern's own number of steps, each hop naming the entities it joins and the last the stable ID of its relationship, so a card's evidence opens, the second reached through an entity without an ID and by a relationship with no usable type, and the notices `supernodesSkipped` and `windowNotApplied`). A spec reaches each state by opening that entity.
